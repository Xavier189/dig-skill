先不要把 Redis 当成既定答案：你真正要解决的是用户列表页在高峰期的 3–4 秒延迟；如果瓶颈是连接池等待、慢 SQL 或查询组合导致的低缓存命中率，加 Redis 只会增加一致性成本，未必降低延迟。

**工作假设**

1. **你真正想要的**：让用户列表页在高峰期也能稳定达到可接受的响应时间，同时不破坏用户数据的可见性；Redis 只是候选手段。
2. **最容易走错的地方**：高峰期特有的慢，更像连接争用或数据库并发压力；而分页、筛选、排序若组合很多，会造成 cache key 爆炸和低命中率。
3. **如果现在必须开始，我会：**
   - ✅ **explicit**：目标对象是 Spring Boot 3 的用户列表查询，高峰期耗时 3–4 秒。
   - 🔍 **delegated**：先用 trace、SQL 执行时间、连接池等待和 `EXPLAIN ANALYZE` 定位耗时，再决定是否引入 Redis。
   - 🔍 **delegated**：只有在“相同查询重复度高且允许短暂陈旧”成立时，才采用 Redis `cache-aside`；否则优先修 SQL、索引或连接争用。
   - ❓ **ambiguous**：允许的数据陈旧时间、当前瓶颈位置和验收延迟目标尚未明确。

请确认下面 3 个会改变方案方向的问题：

1. **这决定 Redis 是否值得做：页面是只在高峰期慢，还是平时也慢？**
   - A. 只在高峰期慢，平时正常
   - B. 平时也慢，高峰期更严重
   - C. 还没有按峰值/非峰值拆分数据
   - **推荐**：若选 C，先采集峰值与非峰值的 `p50/p95/p99`；A 优先查连接池与并发争用，B 优先查 SQL 与索引。

2. **这决定第一步是诊断还是缓存设计：目前 3–4 秒具体耗在哪里？**
   - A. 已确认主要是 SQL 执行
   - B. 已确认主要是获取数据库连接的等待
   - C. 已确认主要在应用层、序列化或网络
   - D. 尚未测量
   - **推荐**：若没有 trace、连接池指标和 SQL 执行计划，选 D，先建立耗时分解；否则无法判断缓存能否命中真正瓶颈。

3. **这决定缓存是否可行以及失效机制：用户被新增、修改或禁用后，列表最迟多久必须反映变化？**
   - A. 必须立即可见
   - B. 可接受 5–30 秒陈旧
   - C. 可接受 1–5 分钟陈旧
   - **推荐**：管理后台涉及禁用/权限状态时选 A；若只是普通浏览列表且业务确认允许短暂陈旧，选 B，方案复杂度和一致性风险更可控。
