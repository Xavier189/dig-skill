# PostgreSQL 迁移执行清单

## 1. 固定执行参数

- [ ] 源库与新库均使用 PostgreSQL，不引入数据库类型变更。
- [ ] 双写持续时间固定为连续 7 天，记录精确的开始与结束时间。
- [ ] 历史数据按稳定主键或唯一键排序迁移；每个常规批次固定 5000 行，尾批处理全部剩余行。
- [ ] 错误率按 `失败行数 / 本批实际处理行数 × 100%` 计算；超过 0.1% 时自动停止迁移流程，0.1% 本身不触发停止。
- [ ] 所有变更操作仅在周日 02:00-04:00 执行；04:00 前停止发起新的变更操作。
- [ ] 回滚仅将读流量切回旧库，不删除、清空或覆盖新库中的任何数据。
- [ ] 将已确定的负责人、审批人及联系方式写入变更单和 on-call 通讯录。

## 2. 变更窗口前准备

- [ ] 完成变更单审批，锁定执行人、审批人、观察人和沟通频道。
- [ ] 确认新库 schema、index、constraint、extension、encoding、timezone、用户权限与旧库一致。
- [ ] 完成旧库备份并验证可恢复性；记录备份时间、位置和校验结果。
- [ ] 部署并验证双写开关、读流量切换开关、迁移暂停开关和断点续跑能力。
- [ ] 确认双写与批量迁移均具备 idempotency，重复执行不会产生重复记录或覆盖更新版本。
- [ ] 准备迁移 checkpoint，至少记录批次号、主键范围、开始时间、结束时间、成功数、失败数和错误率。
- [ ] 准备监控与告警：双写成功率、批次错误率、复制/同步延迟、数据库连接数、CPU、I/O、锁等待、慢查询和应用读写延迟。
- [ ] 验证错误率超过 0.1% 时自动停止当前迁移流程，且不会继续启动下一批。
- [ ] 准备逐批核对脚本：行数、主键集合、关键字段 checksum、缺失记录和重复记录。
- [ ] 完成一次 5000 行预演，验证迁移、核对、自动停止、断点续跑和读流量回切操作。
- [ ] 记录变更前基线：旧库数据量、最新主键/checkpoint、核心接口错误率与 P95/P99 延迟。

## 3. 周日 02:00-04:00 执行

- [ ] 02:00 由负责人宣布变更开始，审批人确认放行。
- [ ] 再次检查旧库、新库、应用实例和监控系统健康状态；任一关键项异常则不启动迁移。
- [ ] 保持读流量指向旧库，开启双写。
- [ ] 写入一组可追踪测试数据，确认旧库与新库均写入成功且内容一致。
- [ ] 启动历史数据迁移，从已记录的 checkpoint 开始，每批处理 5000 行。
- [ ] 每批完成后执行以下检查，再决定是否启动下一批：
  - [ ] 记录成功数、失败数和错误率。
  - [ ] 核对源端与目标端行数、主键及关键字段 checksum。
  - [ ] 确认无重复记录、无遗漏记录、无越界更新。
  - [ ] 确认数据库负载、锁等待和应用延迟未越过既定告警线。
- [ ] 任一批次错误率超过 0.1% 时，由系统自动停止迁移流程并保留 checkpoint、错误明细和现场日志。
- [ ] 对未触发停止的失败记录单独落表或落盘，修复后按 idempotent 方式重放，不静默跳过。
- [ ] 04:00 前不再启动新的变更操作；记录最后一个完整 checkpoint 和当前迁移进度。
- [ ] 负责人更新变更单，审批人确认本窗口结果；双写继续运行直至连续满 7 天。

## 4. 双写 7 天观察期

- [ ] 按开始时间计算连续 7 天双写周期，不提前结束。
- [ ] 持续监控旧库与新库的写入成功率、数据差异、写入延迟和资源使用率。
- [ ] 每日执行增量核对，检查新增、更新、删除事件在两库中的结果一致性。
- [ ] 每日输出差异清单，所有差异必须具备主键、发生时间、来源操作、修复状态和复核结果。
- [ ] 迁移任务或双写链路错误率超过 0.1% 时自动停止迁移流程，保存现场并通知负责人和审批人。
- [ ] 所有补偿与重放操作均从 checkpoint 执行，并在完成后重新进行行数与 checksum 核对。
- [ ] 任何停止、恢复或补偿动作均写入变更单，包含操作者、时间、原因和结果。

## 5. 切换读流量

- [ ] 确认双写已连续运行满 7 天。
- [ ] 确认所有历史批次已完成，尾批剩余数据已处理。
- [ ] 完成全量核对：总行数、主键集合、关键字段 checksum、缺失记录、重复记录和未解决差异均符合验收要求。
- [ ] 确认新库连接数、容量、索引、查询性能和监控告警处于正常状态。
- [ ] 在周日 02:00-04:00 变更窗口内，由负责人申请、审批人放行后，将读流量切到新库。
- [ ] 切流后立即执行核心查询与业务 smoke test，并观察错误率、P95/P99 延迟、连接数、锁等待和慢查询。
- [ ] 记录切流时间、流量状态、验证结果和监控快照。

## 6. 自动停止后的处置

- [ ] 确认迁移流程已经停止，且没有新批次继续执行。
- [ ] 保存当前 checkpoint、失败记录、应用日志、数据库日志和监控快照。
- [ ] 标记触发停止的批次及主键范围，禁止未经修复直接跳过该范围。
- [ ] 由负责人定位并修复错误，完成同范围预演和数据核对。
- [ ] 仅在审批人再次放行且处于周日 02:00-04:00 变更窗口时恢复迁移。

## 7. 回滚执行

- [ ] 由负责人发起回滚，记录触发原因和时间。
- [ ] 将全部读流量切回旧库。
- [ ] 执行旧库核心查询与业务 smoke test，确认读服务恢复正常。
- [ ] 保留新库现有数据和迁移 checkpoint；不得执行 `DROP`、`TRUNCATE`、批量 `DELETE` 或反向覆盖。
- [ ] 保存回滚前后监控快照、路由状态和验证结果。
- [ ] 由审批人确认回滚完成，并在变更单中关闭本次执行。

## 8. 完成验收

- [ ] PostgreSQL 技术栈保持不变。
- [ ] 双写连续运行满 7 天，起止时间和监控证据完整。
- [ ] 常规迁移批次均为 5000 行，尾批处理全部剩余行，所有 checkpoint 可追溯。
- [ ] 错误率超过 0.1% 的场景均已自动停止，无越过停止阈值继续迁移的批次。
- [ ] 全量与增量核对通过，无未解决的缺失、重复或关键字段差异。
- [ ] 读流量切换后的核心查询、业务 smoke test 和监控指标通过。
- [ ] 回滚能力已验证为只切读流量，且新库数据完整保留。
- [ ] 变更单包含负责人、审批人、执行记录、监控证据、核对结果和最终审批结论。
