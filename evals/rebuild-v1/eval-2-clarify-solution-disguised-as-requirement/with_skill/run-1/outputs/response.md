先不要把 Redis 当成既定方案。当前已确认的问题是“用户列表接口在高峰期耗时 3–4 秒”，真正目标应是把它降到明确的 SLO，同时守住数据一致性和故障降级边界。没有 APM、slow SQL、`EXPLAIN ANALYZE` 和请求分布证据时直接加缓存，可能只是掩盖 missing index、慢 `COUNT`、深分页、N+1 或 connection pool saturation；如果列表受租户或数据权限控制，还存在 cache key 不完整导致串数据的风险。这个判断置信度：高。

我建议先按这个工作假设推进：先定位耗时在哪一层并优化根因；只有当查询组合存在稳定热点、重复读比例足够高且业务允许短暂陈旧时，再把 Redis 作为第二层优化。是否采用 Redis 目前仍是 `unresolved`，不是已确认需求。

在给出可实施设计前，需要你确认 3 个会直接改变方案的决策：

1. 性能验收目标是什么？我建议默认按“峰值流量下 `P95 ≤ 500 ms`、`P99 ≤ 1 s`，错误率不升高”验收；如果你只要求平均耗时，尖峰问题会被掩盖。这个默认值是否可接受？
2. 列表允许多旧？
   - 用户新增、禁用、角色/权限变化必须立即可见：需要 write-side invalidation，部分场景应放弃整页缓存。
   - 普通资料允许陈旧 10–30 秒：可考虑短 TTL，并对安全相关变更主动失效。
   - 允许陈旧数分钟：才适合更激进的结果缓存。

   我推荐第二种，但安全相关字段仍要求立即失效。
3. Redis 不可用时，接口应继续查 DB，还是直接失败？我推荐 fail-open 到 DB，但必须配合并发保护、请求合并和限流，否则 Redis 故障会把 DB 一起打垮。

同时我会先核查 endpoint 分段耗时、实际 SQL 与执行计划、筛选/排序/分页组合的热点集中度、峰值 QPS、DB CPU/IO 和 connection pool 等待时间；这些是事实项，不让你凭感觉替我判断。请回复上述 1–3；若你没有额外约束，我就按推荐默认值收敛需求，再给出针对 Spring Boot 3 的落地方案。
