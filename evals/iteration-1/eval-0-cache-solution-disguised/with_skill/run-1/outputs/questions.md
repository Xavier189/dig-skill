## 二、为什么先别急着上 Redis（问题锚点）

只在**高峰期**慢、平峰不慢，这个信号本身就很关键：纯粹的"缺索引/烂 SQL"通常**任何时候都慢**，而"只有高峰慢"往往是**并发/资源**问题（连接池被打满、DB CPU 打满、锁争用）。不同根因下 Redis 的收益天差地别：

| 可能根因 | Redis 缓存能解决吗 | 更对症的做法 |
|---|---|---|
| 缺索引 → 全表扫描 | 部分（命中时快，冷启动/未命中/缓存击穿仍慢） | 加复合索引（可能 30 分钟搞定） |
| 深分页 `LIMIT 100000,20` | 基本不能（每页不同 key，深页几乎不会被缓存） | 改 keyset/seek 分页 |
| ORM N+1（每行懒加载） | 部分 | fetch join / `@EntityGraph` / 批量加载 |
| `SELECT *` 拉大字段 | 部分 | DTO 投影，只查需要的列 |
| 连接池（HikariCP）打满，请求排队 | 基本不能（间接减压） | 调池大小 / 缩短慢 SQL 占用连接的时间 |
| 分页总数 `COUNT(*)` 大表慢 | 部分 | count 单独缓存 / 近似计数 / 延迟计算 |
| 排序字段无索引触发 filesort | 部分 | 给排序字段建索引 |

**核心判断**：很可能一个索引或连接池调整就把 3-4s 干掉了，成本和风险都远低于引入缓存；而缓存会永久背上"一致性 + 失效 + 多一个故障点"的税。所以下面第一批问题优先定位根因。

## 三、第一批问题（根因定位，决定 Redis 是否对症）

### Q1. 你是否已经定位过"慢在哪一层"？
- **A.** 已看过 SQL 执行计划 / 慢查询日志，确认是某条 SQL 慢
- **B.** 只知道接口慢，没具体定位到 DB / 应用 / 资源哪一层
- **C.** 怀疑是 DB，但没真正看过执行计划
- **D.** 有 APM / 慢查询日志 / Arthas 可以随时拉数据
- 👉 **推荐**：若是 B/C，先花 ~30 分钟做一次定位（我可以给你一份诊断清单：`EXPLAIN` 执行计划 + 慢查询日志 + HikariCP 活跃/等待连接数 + 接口分段耗时）。根因没定位就上缓存，是在赌。

### Q2. 平峰期这个页面多快？
- **A.** 平峰也要 1-3s（基本一直慢）
- **B.** 平峰 < 500ms，只有高峰才 3-4s
- **C.** 没量过平峰
- 👉 **推荐**：这条能二分根因——选 A 大概率是索引/SQL 问题（Redis 只是遮盖）；选 B 更像连接池/并发/资源争用（可能调池比加缓存更直接）。麻烦确认下。

### Q3. 列表页的查询长什么样？（可多选）
- **A.** 有分页（page/size 或 offset/limit）
- **B.** 有过滤条件（状态 / 角色 / 时间 / 关键字搜索）
- **C.** 有排序（且排序字段可切换）
- **D.** 就是固定的全量或 Top N，无分页无过滤
- 👉 **推荐**：这决定缓存值不值得做。**A+B+C 组合会让缓存 key 组合爆炸、命中率低、失效极复杂**；只有接近 D 时缓存才简单有效。请贴一下这个接口大致的查询逻辑或 SQL，我判断最准。

### Q4. user 数据多久变一次？能容忍列表"有点旧"吗？
- **A.** 用户数据几乎不变，列表可容忍**分钟级**陈旧
- **B.** 常变（状态/资料常改），但列表能容忍**秒级~分钟级**陈旧
- **C.** 常变，且要求改完/新增后**立即可见**（强一致）
- 👉 **推荐**：A → 缓存最划算，纯 TTL 就行；B → 缓存可行，但要设计写后失效；C → 缓存收益打折且失效逻辑复杂，通常更该去优化查询本身。

## 四、第二批问题（只有确认"确实要上缓存"后才需要回答 —— 缓存落地方案的输入）

### Q5. Redis 现状 + 应用部署形态？
- **A.** Redis 已在用（单机 standalone）
- **B.** Redis 已在用（哨兵 / 集群）
- **C.** 还没 Redis，需要新引入
- **D.** 应用是**多实例**部署（关系到选本地缓存还是分布式缓存）
- 👉 **推荐**：若还没 Redis 且单实例，可先用本地 Caffeine 缓存**零依赖**验证收益，值当了再上 Redis；多实例才有必要直接上分布式缓存。引入新中间件是新组件，先确认收益再背运维成本。

### Q6. 目标延迟 + 峰值量级？
- **A.** 目标 P99 < 500ms，峰值 QPS 约 ______
- **B.** 目标 P99 < 1s
- **C.** 没硬指标，"别卡就行"
- 👉 **推荐**：给个峰值 QPS 数量级即可。它决定要不要做缓存**穿透/击穿/雪崩**防护——低 QPS 下这些是过度设计，高并发下不做会在高峰被打穿（缓存刚失效时全部请求砸向 DB，比现在还糟）。

### Q7. 这次做多大范围？
- **A.** 只解决用户列表页
- **B.** 列表页 + 用户详情页
- **C.** 想借这次搭一套通用缓存层
- 👉 **推荐**：先 A，最小闭环、快速见效、好回滚；验证后再决定要不要推广。别一上来就搭框架（YAGNI）。

## 五、拿到答案后我会怎么做

1. **先出根因结论**：结合 Q1/Q2/Q3 判断真正瓶颈。
   - 若根因是**缺索引 / 深分页 / N+1 / 连接池**——直接给这条路的落地方案（改索引、改分页方式、`@EntityGraph`、调 HikariCP），把 Redis 降级为"可选的二级加速"甚至不需要。**很可能这一步就够了。**
2. **若确认缓存确有必要**（Q3 偏固定列表、Q4 能容忍陈旧）：给出 Redis 落地方案——缓存 key 设计、TTL、写后失效策略（Q4 决定）、穿透/击穿/雪崩防护（Q6 决定是否需要）、本地 vs 分布式选型（Q5 决定）、灰度与回滚步骤，以及一致性风险说明。
