# PostgreSQL 迁移执行清单

## 固定执行参数

| 项目 | 已确认值 |
|---|---|
| 数据库 | 源库、目标库均为 PostgreSQL |
| 双写周期 | 连续 7×24 小时 |
| 回填批次 | 每批 5,000 行 |
| 自动停止阈值 | 错误率 `> 0.1%` |
| 回滚方式 | 仅将读流量切回源库；不删除、清空或回退目标库数据 |
| 变更窗口 | 周日 02:00–04:00 |
| 执行责任 | 使用已确定的负责人和审批人 |

## 1. 变更前检查（最晚周六完成）

- [ ] 在变更单中登记负责人、审批人、执行群、开始时间、结束时间和回滚入口。
- [ ] 确认源库与目标库均为目标 PostgreSQL 版本，字符集、时区、扩展、schema、索引、约束和 sequence 配置一致。
- [ ] 确认目标库容量、连接数、磁盘空间、WAL 增长和 IOPS 可支撑回填及 7 天双写。
- [ ] 确认源库已启用可用的 backup/PITR，并完成恢复可用性检查；本次回滚不依赖删除目标库数据。
- [ ] 验证迁移程序按稳定主键顺序读取，每批固定 5,000 行，支持 checkpoint、幂等重跑和断点续传。
- [ ] 验证双写使用同一业务主键或幂等键，单侧失败可记录、告警并补偿，不向调用方伪报成功。
- [ ] 准备并验证三类校验：总行数、主键集合、关键字段 checksum/聚合值。
- [ ] 配置自动停止规则：
  - 回填错误率：`当前批失败行数 / 当前批尝试行数 × 100%`。
  - 双写错误率：`统计窗口内目标库写失败数 / 目标库写尝试数 × 100%`。
  - 任一错误率严格超过 `0.1%` 时，自动阻止下一批和读流量切换，保留 checkpoint 与错误明细，并立即通知负责人；错误率恰好为 `0.1%` 不触发该阈值。
  - 对完整的 5,000 行批次，失败 6 行及以上即触发自动停止。
- [ ] 在生产等价环境完成 rehearsal，验证 5,000 行批次耗时、锁等待、复制延迟、CPU、IOPS 和自动停止动作。
- [ ] 审批人在变更前确认：脚本版本、监控面板、停止开关、读流量切换开关和回滚命令均已锁定。

## 2. 首个周日 02:00–04:00：启用双写并执行回填

### 02:00 开始

- [ ] 负责人宣布变更开始，记录源库与目标库基线：连接数、QPS、写错误率、延迟、磁盘和 WAL。
- [ ] 启用双写；源库继续承担读流量并保持现有业务写入路径，目标库暂不承担读流量。
- [ ] 用预先准备的测试记录验证 create/update/delete 均同时落入两库，且内容一致。
- [ ] 确认双写错误率未超过 `0.1%` 后开始存量回填。

### 分批回填

- [ ] 每批只处理 5,000 行，不动态扩大批次。
- [ ] 每批完成后持久化 checkpoint，至少记录起止主键、尝试数、成功数、失败数、错误率、开始/结束时间和脚本版本。
- [ ] 每批执行行数、主键集合和关键字段校验；校验通过后才启动下一批。
- [ ] 持续观察源库与目标库的锁等待、慢查询、连接池、CPU、IOPS、磁盘、WAL 和 replication lag。
- [ ] 任一批错误率 `> 0.1%` 时确认自动停止已生效：不得启动下一批，不得切读；源库继续服务，目标库已有数据保持不变。
- [ ] 修复原因后，从最后一个成功 checkpoint 幂等重跑失败批；不得通过跳过失败行来规避阈值。
- [ ] 04:00 前完成本窗口动作；若回填未完成，安全暂停并保留 checkpoint，不在窗口外擅自继续结构或流量变更。

## 3. 连续 7 天双写观察期

- [ ] 源库继续承担读流量；所有业务写入保持双写。
- [ ] 每日核对双写尝试数、成功数、失败数、补偿积压和错误率。
- [ ] 每日执行增量行数、主键和关键字段校验，差异必须形成可追踪记录并完成补偿。
- [ ] 双写错误率 `> 0.1%` 时自动冻结后续迁移与切读动作，通知负责人和审批人；不得删除目标库数据。
- [ ] 处理观察期内新增、更新、删除数据，确保删除语义和 sequence/identity 值在两库一致。
- [ ] 满 7×24 小时后生成最终 reconciliation 报告；存在未解释差异、失败补偿或错误率超阈值记录未闭环时，不进入切读。

## 4. 下一周日 02:00–04:00：切换读流量

- [ ] 负责人确认双写已连续运行满 7×24 小时。
- [ ] 审批人核验最终 reconciliation 报告、监控状态和回滚入口，并在变更单中批准切读。
- [ ] 切换前记录两库最终 checkpoint、行数、关键字段 checksum 和当前读流量路由。
- [ ] 将读流量切换至目标 PostgreSQL；切换期间继续双写，不自动停止源库写入。
- [ ] 验证目标库读请求成功率、业务错误率、P95/P99 latency、连接数和慢查询。
- [ ] 执行核心业务 smoke test，覆盖查询、新增后读取、更新后读取和删除后不可见。
- [ ] 确认 100% 读流量已到目标库，且源库不存在意外读流量。
- [ ] 保留源库、目标库数据、双写能力、checkpoint、日志和 reconciliation 报告；停止双写应作为后续独立受控变更执行。

## 5. 自动停止后的处置

- [ ] 确认迁移程序停止领取新批次，读流量仍在当前已验证安全的一侧。
- [ ] 保存失败批次、失败 SQL/错误码、主键范围、应用版本、数据库指标和 trace，不修改或清理目标库现场数据。
- [ ] 判断失败记录是否已在源库成功；以源库事实和 checkpoint 生成补偿集。
- [ ] 修复后先对失败批次执行 dry-run 和校验，再由负责人恢复迁移。
- [ ] 恢复后仍按每批 5,000 行执行；不得临时放宽 `0.1%` 阈值。

## 6. 回滚清单

- [ ] 负责人触发回滚时，只将读流量切回源库。
- [ ] 验证 100% 读流量已回到源库，核心读接口和业务 smoke test 正常。
- [ ] 保持源库业务写入可用；双写链路健康时继续双写，以免扩大两库差异。
- [ ] 不执行目标库 `DELETE`、`TRUNCATE`、drop schema、恢复旧 snapshot 或反向覆盖。
- [ ] 冻结新的迁移批次和再次切读，保留目标库现有数据、WAL、checkpoint、日志和差异记录用于排障。
- [ ] 在变更单记录回滚时间、触发指标、影响范围、两库数据差异和后续恢复条件，由负责人提交、审批人确认。

## 7. 完成证据

- [ ] 双写连续运行满 7×24 小时，期间所有 `> 0.1%` 事件均已自动停止并闭环。
- [ ] 全部批次均为 5,000 行或最后一个不足 5,000 行的尾批，且每批都有 checkpoint 和校验记录。
- [ ] 最终总行数、主键集合和关键字段校验无未解释差异。
- [ ] 读流量切换后核心业务 smoke test、错误率和 latency 达标。
- [ ] 变更单已附脚本版本、监控截图、批次日志、reconciliation 报告、审批记录和实际时间线。
