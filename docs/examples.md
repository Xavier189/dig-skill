# 跨领域输入与探索示例

判断任务是否需要探索，依据请求活动、相关前提和影响是否已经核验。描述清楚、输入短小或给出代码，不单独决定跳过。

## 需求清楚，仍有值得调查的内容

| 输入 | 主动核验 | 对话或设计的价值 |
|---|---|---|
| “加个限流开关，默认关闭，不再返回限流失败。” | 已有开关、默认值、统计与拦截是否分离 | 避免重复机制，准确解释关闭后的行为 |
| “报表增加几个字段，计算公式已经写好。” | 来源事件、关联键、输出时机、缺字段与未发生的区别 | 找到正确字段所需的最小等待、降级与日志设计 |
| “直接提交改成 worker 主动拉取。” | 受理、排队、执行、容量、登记、重试与完成链路 | 让成功与并发等词的含义成为可验证契约 |
| “重试后偶尔出现两次任务，帮我解决。” | 请求、回执、重试和去重证据 | 解释原因与修复影响，不先要求用户自己整理链路 |
| “周会改成文字更新，每周一提交。” | 现有会议的同步、决策、协调用途 | 找到必须保留的能力，不自行引入新的会议治理体系 |
| “这个提案已经很完整，帮我看看。” | 关键前提、参与者、依赖与可验证的后果 | 明确表达也能包含未经检验的假设 |

这些场景进入探索不代表必定要提问。查到已有机制、证据足够且没有真实取舍时，可以直接给出有依据的设计，并按已有授权继续。

## 相近输入，合理的不同处理

| 输入 | 处理 |
|---|---|
| “只查现在的限流开关默认值。” | 读配置与代码，直接回答事实 |
| “开关与受影响路径已核验，按已确认方案改默认值。” | 继承决定并执行，不重新访谈 |
| “把 README 标题改成这个名字，其他不动。” | 机械修改 |
| “导出规则都写完了，现在实现。” | 核验规则与当前权限、数据和输出契约；未核验的影响不能仅因“写完”而跳过 |
| “只查接口变慢的根因，不讨论方案。” | 诊断与证据交付，不扩大为偏好问卷 |
| “我想做一个自己的小程序，还不知道做什么。” | 用具体方向与判断依据帮助探索 |
| “按已定规则连接两份 CSV，只输出结果。” | 数据转换，不调用 STRUCTURE |
| “把已确认与暂缓事项整理给下一轮。” | 保存共享决定及其状态 |

## 让知识与回答改变方案

用户不知道应选哪种队列时，先说明与本任务有关的领取、确认、丢失和重复行为，再讨论可以接受的结果。不能用“更可靠”直接强推新组件。

用户说明“允许重启时丢失，但正常运行不能重复处理”后，只更新这些选择。不能把它解释为允许任何情况下都丢数据，也不能认为重试与业务幂等不再相关。

用户说某种事件已经停止使用时，撤掉依赖其存在的结论，同时保留不依赖该事件的重复处理问题。源码残留不证明线上还有流量；用户的环境前提应标明来源，不扩成通用平台事实。

## 深入不等于扩范围

新增字段可能确实需要关联异步事件、区分未知与零值、记录取值失败原因。发现现有消息链路没有端到端事务，不自动要求引入 exactly-once、重写所有出口或建立多阶段发布体系。

每个修正说明它如何影响当前字段的正确性或现有行为。不属于当前目标的改进单独保留，不写成硬验收项。

## 续聊、授权与完成

| 后续输入 | 应如何继续 |
|---|---|
| “只统计真正开始处理的，继续。” | 更新统计含义，继续当前活动；不确认其他选择 |
| “我不懂你说的两种方案。” | 解释本任务中的可观察差别，让用户有判断依据 |
| “其他沿用现有行为，现在实现。” | 查证可获得的现状，在授权范围内继续 |
| “先检查，没有实质问题就直接改。” | 检查后执行，不增加批准环节 |
| “审一下就行，不要改文件。” | 交付发现、建议与证据限制，允许未决项存在 |
| “我们已讨论过，换个 session 接着做。” | 恢复决定，仅刷新缺失或可能变化的证据 |

深度以理解和设计的改善衡量，不以问题轮数、文件数量或文档篇幅衡量。
